PostgreSQL安全删除表插件：pg_safe_drop
梧杵 元婴问道
  2025-09-04 12:06:04   2025-09-04 14:39:22  
  • PostgreSQL
  • ProcessUtility Hook
  

在 PostgreSQL 数据库的管理中，删除表（DROP TABLE）操作通常是一个不可逆的过程。当用户执行删除操作时，相关数据会被永久丢弃，除非事先做好备份。然而，在实际生产环境中，删除表有时可能是一个错误操作，或者是需要暂时“隐藏”某些表而非完全删除。为了防止误删重要数据，提出了一个“安全删除”功能：即在执行 DROP TABLE 时，表不会被删除，而是被移动到一个名为“回收站”（trashcan）的 schema 中。

pg_safe_drop 插件的目标与功能

pg_safe_drop 插件通过拦截 PostgreSQL 的 DROP TABLE 命令，将待删除的表移动到指定的回收站 schema 中，而不是完全删除。这种方式可以有效避免误操作，同时在不需要时可以通过恢复的方式找回表和数据。

实现的主要功能：

  1. 拦截 DROP TABLE 操作： 通过定制的 ProcessUtility hook，拦截用户执行的 DROP TABLE 命令，避免直接删除表。
  2. 将表移入回收站 schema： 在执行删除命令时，将表移动到指定的回收站 schema 中，表结构和数据保持不变。
  3. 处理多个表删除： 支持一次性删除多个表，并将它们一并移动到回收站 schema。
  4. 跳过特殊表： 跳过系统表（如 pg_catalog）、临时表（pg_temp）、TOAST 表等不需要被移动的表。
  5. 避免重复表名： 如果回收站中已有同名表，会通过时间戳重命名，以避免冲突。
  6. 可配置性： 插件支持通过 GUC（Grand Unified Configuration）参数进行配置，可以自定义回收站 schema 的名称以及是否启用安全删除功能。
  7. 表的 schema 迁移： 插件使用 ALTER TABLE … SET SCHEMA 命令将表迁移到回收站 schema 中，而不是直接删除表。

实现原理

pg_safe_drop的核心是通过钩子（hook）机制拦截 PostgreSQL 内部的 SQL 命令流。具体来说，插件通过 ProcessUtility hook 函数，在每次执行 SQL 语句时被触发，检查语句是否为 DROP TABLE，如果是，则执行相应的逻辑。

  1. 模块初始化：
    在 pg_safe_drop 插件加载时，首先通过 _PG_init() 函数定义了两个 GUC 参数：pg_safe_drop.safe_drop_schema（指定回收站 schema 的名称）和 pg_safe_drop.safe_drop_enabled（控制插件是否启用）。插件会尝试创建指定的回收站 schema（如果不存在的话）。

  2. 拦截 DROP TABLE 命令：
    pg_safe_drop_ProcessUtility 函数是插件的核心，主要处理 DROP TABLE 命令。当系统执行 DROP TABLE 时，插件会首先检查命令的类型：

    • 如果是 DROP TABLE，则会执行表的迁移操作，而非删除。
    • 如果命令中包含多个表，插件会依次处理每个表。

  3. 回收站 schema 的创建：
    如果指定的回收站 schema 尚不存在，插件会创建一个新的 schema，并确保它对当前数据库用户可见。

  4. 表的移动：

    • 检查表是否存在： 插件会检查每个表是否存在于当前数据库中，并跳过不存在的表。
    • 跳过系统表、临时表、TOAST 表： 插件会过滤掉系统表、临时表和 TOAST 表，避免误操作。
    • 处理同名冲突： 如果回收站 schema 中已存在同名表，插件会自动给新表添加时间戳后缀，以确保名称唯一性。

  5. ALTER TABLE SET SCHEMA：
    使用 ALTER TABLE … SET SCHEMA 将表从原 schema 移动到回收站 schema 中。

  6. 完成操作：
    插件执行完表的迁移后，输出日志通知管理员操作已完成。

ProcessUtility Hook介绍

Hook（钩子） 是一种编程模式，允许开发者在程序的特定点插入自定义逻辑或行为，而不需要修改原始代码的结构。它是操作系统、库、框架或者应用程序中用于扩展功能的一种机制。通过钩子，开发者可以“挂钩”到程序执行的关键位置，拦截事件或函数调用，并添加自定义的操作。

ProcessUtility Hook 是 PostgreSQL 中的一种钩子机制，它允许扩展在处理 DDL（数据定义语言）命令时插入自定义逻辑。ProcessUtility 函数本身是 PostgreSQL 用来解析和执行 DDL 命令（如 CREATE, DROP, ALTER 等）的一部分，而 ProcessUtility Hook 使得开发者可以在执行这些命令之前拦截并修改它们，或添加额外的行为。它定义在 src/include/tcop/utility.h 文件中，具体如下：

扩展初始化过程

_PG_init是PostgreSQL扩展的模块初始化函数和入口点，必须是非静态函数且不能更改函数名。它在扩展首次加载时被调用，负责完成所有必要的初始化工作，包括GUC参数定义、hook注册、数据结构初始化等。

在pg_safe_drop里面，_PG_init按以下步骤初始化：

  • 定义GUC参数：注册配置参数控制扩展行为
  • 保存原hook：prev_ProcessUtility = ProcessUtility_hook
  • 安装新hook：ProcessUtility_hook = pg_safe_drop_ProcessUtility

pg_safe_drop_ProcessUtility

  1. 解析表名：使用makeRangeVarFromNameList将对象名列表转换为RangeVar结构
  2. 验证表存在性：通过get_relname_relid检查表是否存在
  3. 跳过保护表：过滤系统表、临时表和TOAST表
  4. 处理重名冲突：如果回收站中存在同名表，先重命名
  5. 执行schema移动：构造AlterObjectSchemaStmt并调用standard_ProcessUtility
