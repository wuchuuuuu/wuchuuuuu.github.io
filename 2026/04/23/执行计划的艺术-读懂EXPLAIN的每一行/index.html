执行计划的艺术：读懂EXPLAIN的每一行

写 SQL 的人有很多，但能读懂执行计划的人不多。EXPLAIN 是 PostgreSQL 给程序员的一盏灯——它照见查询的每一步去向，也照见优化器的每一次抉择。这篇文章，我们把这盏灯彻底点亮。

🔦 EXPLAIN 是什么？

简单说，EXPLAIN 让 PostgreSQL 把它打算怎么执行 SQL 的方案告诉你，而不真的去执行。

短短两行里藏着：访问方式、成本估算、行数估算、列宽估算、过滤条件——每一项都值得细细品味。

🧪 EXPLAIN 的几种形态

命令 作用
EXPLAIN 只显示计划，不执行
EXPLAIN ANALYZE 真的执行，给出真实耗时和行数
EXPLAIN (BUFFERS) 显示缓冲区命中情况
EXPLAIN (VERBOSE) 显示完整的列信息
EXPLAIN (FORMAT JSON) 机器友好的输出，适合自动化

🎯 cost 的正确打开方式

  • 0.29：启动成本——返回第一行前的估算代价
  • 8.30：总成本——完成所有行返回后的估算代价
  • rows：估算返回的行数
  • width：每行的平均字节数

cost 的单位不是秒、不是毫秒，是”逻辑代价单元”——一个内部的相对值，基于以下参数组合：

参数 默认值 含义
seq_page_cost 1.0 顺序读一页的成本
random_page_cost 4.0 随机读一页的成本
cpu_tuple_cost 0.01 处理一行的 CPU 成本
cpu_index_tuple_cost 0.005 处理一个索引条目的 CPU 成本
cpu_operator_cost 0.0025 一个操作符的 CPU 成本

💡 SSD 时代，把 random_page_cost 调到 1.1~1.5 往往能让优化器更偏爱索引扫描。

🧭 常见的扫描方式

Seq Scan（顺序扫描）

顺序读整张表。当选择性差或表小时，这反而是最优选择。

Index Scan

走索引找到 ctid，再回表。适合高选择性的等值/范围查询。

Index Only Scan

所有需要的列都在索引里，完全不回表。Heap Fetches: 0 是最漂亮的结果。

Bitmap Heap Scan / Bitmap Index Scan

适合中等选择性：先用索引收集所有候选 ctid 形成位图，再按块顺序批量读堆表。减少随机 I/O，效果拔群。

🔗 三种 JOIN 算法

Nested Loop（嵌套循环）

外表每一行 × 内表查一次。适合外表小、内表有索引。

Hash Join

把小表建哈希表，大表逐行探测。适合等值连接且内存够用。

Merge Join

两表都排好序再归并。适合大表 + 已有序（或可用索引有序扫描）。

⏱️ ANALYZE 的黄金信息：actual vs estimated

EXPLAIN ANALYZE 会同时给出估算和实际：

估算 5 行，实际 50000 行 ——优化器被严重误导了，这种查询大概率跑错计划。

原因通常是：

  • 统计信息过期：ANALYZE table_name; 更新
  • 列分布倾斜：提高 default_statistics_target
  • 多列相关性：使用 CREATE STATISTICS 建立多列统计

“estimated 和 actual 差 100 倍以上” 是优化器识别的警报灯。

🎨 读 EXPLAIN 的正确姿势

执行计划是一棵树，从内向外、从下往上读：

阅读顺序：

  1. Seq Scan on orders（外表）
  2. Seq Scan on users → Hash（建哈希表）
  3. Hash Join（连接）
  4. Sort（排序输出）

🛡️ 优化器会”说谎”吗？

优化器从不说谎，但可能被骗。它完全依赖：

  • 统计信息：pg_statistic / pg_stats
  • cost 参数：如 random_page_cost
  • 配置：work_mem 决定能否用 hash / sort
  • planner 相关开关：如 enable_seqscan = off

优化器是数学家，不是魔术师——喂什么统计信息，它就画什么计划。

✨ 结语

EXPLAIN 不只是”查询计划的字面解释”，它是数据库与你对话的方式。

它会告诉你：

  • 它以为你要几行
  • 它打算怎么取数据
  • 它最终跑成什么样

读懂它，你就从一个”写 SQL 的人”成长为”与优化器合作的人“。

写 SQL 像讲话，读计划像听话——会听的人，才写得好。
