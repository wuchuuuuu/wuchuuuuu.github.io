慢查询是怎么炼成的：从pg_stat_statements说起
梧杵 化神洞玄
  2026-04-23 21:55:00   2026-04-23 21:16:35  
  • PostgreSQL
  • 性能分析
  • pg_stat_statements
  

每一个被优化掉的慢查询背后，都藏着一位不眠不休的侦探。
在 PostgreSQL 世界里，这位侦探的名字叫 pg_stat_statements——它不抓贼，但它比谁都清楚”谁是贼”。本文带你系统地掌握它、用好它。

🕵️ 没有它之前，我们是怎么找慢查询的？

然后你得：

  1. 手写脚本或用 pgBadger 扫日志
  2. 聚合相同模式的 SQL
  3. 找出耗时大头

这个做法能跑，但有几个痛点：

  • 日志体积恐怖：高并发下写爆磁盘
  • 不能实时：等日志落盘再分析
  • 聚合靠自己：字面不同但语义相同的 SQL 很难合并

这时候就需要一个”常驻内存“、”自动聚合“、”秒级查询“的工具——pg_stat_statements 正是为此而生。

🧬 它能告诉你什么？

每一列都是一把钥匙：

字段 含义
query 归一化后的 SQL（参数位被 $1 替代）
calls 调用次数
total_exec_time 执行总耗时（ms）
mean_exec_time 单次平均耗时
stddev_exec_time 耗时标准差（看抖动）
rows 返回行数总和
shared_blks_hit shared_buffers 命中块数
shared_blks_read 从 OS/磁盘读取的块数
shared_blks_dirtied 修改的脏块数
wal_records 产生的 WAL 记录数（PG 13+）
temp_blks_read/written 临时文件读写（大排序/大 hash 的信号）

关键洞察：它把字面不同、模式相同的 SQL 自动归成一条——这就是归一化（normalization）。

🎯 排 TOP 慢查询的三种姿势

1. 按”总耗时”排（最常用）

适用：找”消耗资源最多”的 SQL——通常是优化最值得做的。

2. 按”单次耗时”排

适用：找”每次都很慢”的 SQL——通常是索引缺失或执行计划烂。

3. 按”I/O 消耗”排

适用：找缓存不命中多的查询——可能是全表扫描或工作集超过 shared_buffers。

在实践中，不同类型的慢 SQL 会留下不同的”指纹”：

指纹 1：全表扫描

常见解：加索引、改写查询、加过滤条件。

指纹 3：每次只返回 1 行但调用 100 万次

常见原因：N+1 查询、应用层循环。
解法：批量化查询、加缓存、用 IN (...) / JOIN 合并。

指纹 4：stddev 巨大

常见原因：执行计划在某些参数下突变，典型 “plan flip“。
解法：EXPLAIN ANALYZE 对比不同参数、检查统计信息。

🎨 归一化的陷阱

pg_stat_statements 的归一化不是万能的：

  1. 使用字面量拼接 SQL 会导致每条都不同（如 ORM 生成的 SQL 有时很糟糕）：
  2. DDL 不会归一化：每一次 CREATE TABLE xxx 都是独立记录
  3. 注释不同也会被视作不同 SQL（除非开 pg_stat_statements.track_utility = off）

实战建议：优先让应用使用参数绑定（prepared statement），而不是 SQL 字符串拼接。

🔁 重置统计：什么时候该清零？

适合的时机：

  • 上线新版本后：观察新 SQL 的负载画像
  • 优化完某条 SQL 后：验证效果
  • 诊断瞬时问题：先 reset，再等几分钟再看

不适合：日常定期 reset —— 会失去长期趋势视角。

📈 搭配时间维度：pg_stat_kcache / auto_explain

auto_explain：自动抓慢查询的执行计划

超过 500ms 的 SQL 会把完整 EXPLAIN ANALYZE 计划写进日志。
从此不再需要线下复现 SQL，生产现场就是证据。

pg_stat_kcache：更细的 I/O 数字

这个扩展能告诉你：实际发生的系统调用、CPU 时间、读/写字节数。
与 pg_stat_statements 合并使用，能精准回答”这条 SQL 到底把时间花在哪里“。

✨ 结语

性能优化的起点，不是猜测，而是测量。

pg_stat_statements 给了你一双看穿生产流量的眼睛：

  • 它告诉你谁最贪心
  • 它告诉你谁最反复
  • 它告诉你谁最不稳定

而你要做的，就是每天读一眼这张表，像医生查房一样。

能看到慢查询的人，才有资格谈性能优化。
