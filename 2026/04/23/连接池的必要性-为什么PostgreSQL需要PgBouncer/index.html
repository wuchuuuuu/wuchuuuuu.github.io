连接池的必要性：为什么PostgreSQL需要PgBouncer
梧杵 化神洞玄
  2026-04-23 21:40:00   2026-04-23 21:13:18  
  • PostgreSQL
  • 连接池
  • PgBouncer
  

一个不起眼的连接问题，往往是压垮 PostgreSQL 最后一根稻草。
数据库连接为什么这么贵？PgBouncer 凭什么能成为 PG 社区的事实标准？这篇文章，我们从进程模型讲到实战调优，彻底理清连接池的必要性。

🧠 一切从”进程”开始

PostgreSQL 的架构有一个重要设定：

每一个客户端连接，对应数据库一个独立的后端进程（backend process）。

不是线程、不是协程、是一个实打实的 OS 进程。

这种设计带来稳定性（一个连接崩溃不影响别人），但也带来昂贵的代价。

💸 一个连接到底有多贵？

创建一个 PG 连接，要付出：

  1. fork 一个进程：大约 1~3ms，消耗 CPU
  2. 分配 backend 专属内存：work_mem、temp_buffers 等 per-backend 结构
  3. 建立共享内存映射：attach shared_buffers
  4. 认证：密码校验、SSL 握手
  5. 初始化：设置 session GUCs、解析搜索路径

综合下来，每个空闲连接光是结构体就占 5~10MB；一旦开始跑查询，work_mem 默认 4MB，复杂查询可能瞬间吃掉几百 MB。

1000 个空闲连接 ≈ 5~10GB 内存白白被占用。

这就是为什么 PG 社区有那句名言：

“Idle connections are not free.”

🎢 context switch 才是更大的坑

1000 个 backend 同时在 CPU 核心之间切换，会让：

  • 调度器过载：内核花大量时间在 context switch
  • 缓存污染：每次切换都刷 L1/L2 cache
  • 锁竞争加剧：lwlock 的等待队列变长

实测：同一套硬件，50 个连接跑 TPS 可能比 500 个连接还高。

🧮 该开多少连接？

一个经验公式：

  • 32 核 SSD 机器：大约 60~100 个连接够用
  • 64 核 NVMe 机器：100~200 个连接

超过这个数值，吞吐量会停止增长甚至下降（著名的 knee point）。

但现实是——应用端动辄几百上千个连接怎么办？

答案：放一个”代理人”在中间——这就是连接池。

🏊 连接池：共享即优雅

连接池的核心思想只有一句：

少量的数据库连接，服务大量的客户端连接。

客户端感知不到变化——它依然以为自己直连数据库，只是中间有一层”接线员”在高效派单。

🚰 PgBouncer 的三种池化模式

这是 PgBouncer 最重要的一个概念，决定了连接能在什么粒度上被复用。

1. session 模式

客户端断开前，这个后端连接一直属于它。

  • ✅ 兼容性最好，支持所有 SQL 特性
  • ❌ 复用率等于 0，几乎没池化效果

2. transaction 模式（最常用）

每个事务开始时借一个后端，事务结束归还。

  • ✅ 复用率高，生产环境最佳平衡
  • ⚠️ 不支持 session 级特性（如 SET、prepared statements、LISTEN/NOTIFY）

3. statement 模式

每条语句都可能拿到不同的后端。

  • ✅ 极致复用
  • ❌ 多语句事务直接崩，基本只用于纯只读查询

⚠️ transaction 模式的”陷阱清单”

既然生产上几乎都用 transaction 模式，就必须知道它不支持什么：

特性 问题描述
SET / SET LOCAL 会话变量可能”漂移”到别的后端上
PREPARE / EXECUTE 预编译语句绑定在后端进程上
LISTEN / NOTIFY 通知机制依赖长连接
临时表 TEMP TABLE 同样是 session 私有
游标 / WITH HOLD 游标 事务结束即失效
服务端参数 application_name 动态改 会飘

应用侧要做的事：

  • 使用 SET LOCAL（随事务结束自动还原）
  • 改用客户端预处理（如 JDBC 的 useServerPrepStmts=false）
  • 跨事务状态改用表或 Redis存储

🛠️ 一份生产级 PgBouncer 配置

关键参数解释：

  • default_pool_size：决定每个用户+数据库组合最多用多少 PG 连接
  • max_client_conn：PgBouncer 能容纳多少客户端连接（只占 PgBouncer 的内存）
  • max_db_connections：对整个 PG 实例的并发上限

典型配比：max_client_conn = 5000，default_pool_size = 25 → 200 倍放大，但 PG 始终只扛 25 个真实连接。

🔍 PgBouncer 的”内省”

连接到管理端口后（默认走 pgbouncer 数据库）：

SHOW POOLS 的输出是观察核心：

  • cl_waiting 高：说明池子不够大
  • maxwait 持续高：客户端在排队
  • sv_idle 长期为 0 + cl_waiting 高：典型需要扩池子的信号

🧭 还有哪些选择？

方案 特点
PgBouncer 轻量、C 实现、事实标准，transaction 模式王者
Pgpool-II 功能更重（读写分离、负载均衡、查询缓存）
Odyssey Yandex 开源，多线程，支持更大规模
应用内连接池（HikariCP 等） 属于”客户端连接池”，和 PgBouncer 是两层
PG 14+ 原生 依然没有官方连接池，社区曾经有 connection_pool 提案但未合入

常见组合：HikariCP（应用内）+ PgBouncer（前置代理），形成两级池。

🧨 一个真实的”血案”

某应用在 Kubernetes 里部署了 30 个 Pod，每个 Pod 开了 50 个 HikariCP 连接 → 1500 个直连。

问题表现：

  • PG 占用内存 20GB 以上仅用于 idle backend
  • CPU 负载高，但 TPS 反而上不去
  • 偶发 FATAL: remaining connection slots are reserved

加一层 PgBouncer 后：

  • PG 实际 backend 降到 80
  • 内存释放 15GB
  • TPS 提升 40%，延迟下降 60%

这不是魔法——只是让数据库回到它最擅长的并发区间。

✨ 结语

PostgreSQL 并不弱，它只是对连接数有自己的脾气。

连接池不是”性能优化”，而是架构的必要组件——
像自来水厂前的水塔，像高速公路的收费站。

直接连 PostgreSQL 的应用，都该问自己一句：真的不需要 PgBouncer 吗？
