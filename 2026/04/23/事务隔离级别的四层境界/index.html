事务隔离级别的四层境界

一个人最容易误解的技术概念，事务隔离级别一定排得上前三。
我们耳熟能详的 READ UNCOMMITTED / READ COMMITTED / REPEATABLE READ / SERIALIZABLE 到底是什么？PostgreSQL 为什么和 SQL 标准”貌合神离”？这篇文章一次讲清。

🧩 事务的四大”烦恼”

理解隔离级别，要先理解它为了解决什么问题。并发事务下有四种异常：

1. 脏读（Dirty Read）

读到了别的事务还没提交的数据：

2. 不可重复读（Non-repeatable Read）

同一事务内读两次同一行，结果不同：

3. 幻读（Phantom Read）

同一事务内两次范围查询，结果集”多”或”少”了行：

4. 序列化异常（Serialization Anomaly）

每个事务单独看都合法，但组合起来，结果却是任何串行顺序都无法产生的。这是最微妙的一种。

📜 SQL 标准的四层隔离

SQL 标准用这四种异常来划分隔离级别：

隔离级别 脏读 不可重复读 幻读 序列化异常
READ UNCOMMITTED 可能 可能 可能 可能
READ COMMITTED ❌ 可能 可能 可能
REPEATABLE READ ❌ ❌ 可能 可能
SERIALIZABLE ❌ ❌ ❌ ❌

级别越高，隔离越强，但性能代价越大。

🐘 PostgreSQL 的”实事求是”

PostgreSQL 的实现并不完全照搬标准，它基于 MVCC 做了更强的保证：

级别 PG 实际行为
READ UNCOMMITTED 等同于 READ COMMITTED（MVCC 下脏读天然不可能）
READ COMMITTED 默认级别；每条 SQL 看到已提交快照
REPEATABLE READ 整个事务看到同一个快照；不允许幻读
SERIALIZABLE 基于 SSI（Serializable Snapshot Isolation）

PG 的 READ UNCOMMITTED 严格等于 READ COMMITTED，因为 MVCC 的快照机制决定了它读不到未提交数据。

🔬 READ COMMITTED：默认的温柔

PostgreSQL 的默认隔离级别。规则是：

每条 SQL 语句开始时拿一个新的快照。

这对写少读多的 OLTP 系统最友好：代价小、并发高。
但它无法避免不可重复读和幻读。

🪞 REPEATABLE READ：一事一世界

在 PostgreSQL 里，REPEATABLE READ 的实际效果是：

事务内所有 SQL 使用同一个快照（事务开始时的快照）。

特别的一点：在 PG 里，REPEATABLE READ 已经不存在幻读——因为它用的是一致性快照，不是锁范围。
这比 SQL 标准要求的 REPEATABLE READ 更严格。

代价：写写冲突

🧠 SERIALIZABLE：最强隔离的艺术

PostgreSQL 9.1 起提供了 SSI（Serializable Snapshot Isolation）。
这是一个极其精巧的算法，能在快照隔离的基础上，检测出任何导致序列化异常的执行顺序。

它不像传统 2PL（两阶段锁）那样粗暴加锁，而是：

  1. 每个事务仍然基于快照运行（高并发）
  2. 系统追踪事务之间的读写依赖
  3. 如果发现形成”危险环“，就选一个受害者事务回滚

💡 快照、可见性与 MVCC 的关联

一个 PostgreSQL 快照本质上是这样的三元组：

一行元组是否可见，靠它的 xmin、xmax 与快照对比：

  • xmin 已提交且不在活跃列表 → 这行存在
  • xmax 未设置 / 未提交 / 在活跃列表 → 这行没被删除

快照 + 元组头 = MVCC 的可见性判定。事务隔离就建立在这个基础上。

🎯 该用哪个级别？

场景 建议级别 理由
普通 OLTP READ COMMITTED 性能最高，满足 99% 业务
需要事务内一致读的报表查询 REPEATABLE READ 避免数据飘移
转账、库存扣减等强一致 SERIALIZABLE 防止复杂并发异常
对账脚本 REPEATABLE READ 配合 pg_export_snapshot 可跨会话一致

选择原则：先用最低够用的，遇到问题再升级。

🚨 几个”致命”的陷阱

陷阱 1：误以为 READ COMMITTED 能保证”读写原子性”

注意：UPDATE ... WHERE 使用的是最新快照（防止丢失更新），所以这是安全的。
但先 SELECT 再根据值 UPDATE 是不安全的，需要：

  • 用 SELECT ... FOR UPDATE 加行锁
  • 或升级到 REPEATABLE READ / SERIALIZABLE

陷阱 2：SERIALIZABLE 一定不会错？

会错。当 SSI 检测到冲突，它会主动回滚事务。
不做自动重试的话，业务就会吃到随机失败。

陷阱 3：长事务让 MVCC 心力交瘁

高隔离级别的事务越久，未完成快照越多，VACUUM 越无能为力。
永远不要在前端交互中开启长事务。

✨ 结语

事务隔离级别不是选择题，而是权衡题：

  • 性能 vs 一致性
  • 简单 vs 严谨
  • 默认 vs 精准

PostgreSQL 用 MVCC 给了我们一条读写不互斥的高速公路，
再用 SSI 给了我们严格串行化的安全带。

好的工程师不追求最高隔离，只追求刚刚好的隔离。
