分区表的使用哲学：什么时候该拆，怎么拆才优雅
梧杵 化神洞玄
  2026-04-23 21:45:00   2026-04-23 21:14:07  
  • PostgreSQL
  • 分区表
  • partition
  

有人说：“分区表是治表巨大的灵丹”；也有人说：“乱用分区表，是把简单问题搞复杂的艺术”。两种说法都对。本篇文章，我们聊透 PostgreSQL 的分区表——什么时候该拆、怎么拆才优雅、它的坑在哪里。

🌳 为什么要分区？

想象一张 100 亿行的 orders 表：

  • 维护困难：一次 VACUUM 可能几小时跑不完
  • 数据冷热混杂：去年的订单和今天的订单挤在一起
  • 索引巨大：B-Tree 高度变高，命中也慢
  • 删除代价高：删 2020 年的数据全走 DELETE + VACUUM

分区表的核心思想很朴素：

把一张大表按照某种规则，拆分成多张小的子表，对外仍然以一张表的身份存在。

🧩 PostgreSQL 的分区演进

时代 方案 痛点
PG < 10 继承 + 触发器（手工分区） 又繁琐又易错
PG 10 声明式分区首次登场 功能有限，没有 PK
PG 11+ 哈希分区、外键支持 真正可用
PG 13+ 分区级 JOIN、分区裁剪优化 性能大跃进
PG 14+ 分离式 DETACH CONCURRENTLY 运维更温柔

现在（PG 14+）的声明式分区已经足够好用，不必再用触发器方案了。

🎯 三种分区类型

1. RANGE（范围分区）

按值的范围划分。最常见——按时间。

适用场景：时间序列、冷热分离、按区间归档。

2. LIST（列表分区）

按枚举值划分。

适用场景：按地域、按租户、按业务线拆分。

3. HASH（哈希分区）

按哈希值均匀分布。

适用场景：无自然范围、无枚举值，但希望打散到多个文件降低单表压力。

🎛️ 分区裁剪（Partition Pruning）

分区表的性能关键词。PostgreSQL 在执行 SQL 时，会智能地只扫描相关的子分区：

两种裁剪时机：

  • Plan Time Pruning（默认）：查询计划生成时就裁掉
  • Runtime Pruning（PG 11+）：执行时才知道值（如预编译参数），也能裁

查询条件必须包含分区键，否则裁剪失败，会扫描所有子表，收益瞬间归零。

🧊 冷热分离：分区表的”招牌菜”

一秒删三年数据，这就是分区表带来的优雅。
对比没分区时的 DELETE FROM orders WHERE created_at < '2025-01-01'; 哪一个更温柔，不言而喻。

🪢 外键、唯一约束与分区

这里是新手最容易踩坑的地方：

分区表上的 UNIQUE / PRIMARY KEY 必须包含分区键！

为什么？因为唯一性只能在单个分区内部保证，要让整表唯一，唯一列必须”告诉”数据库它属于哪个分区——分区键必须在里面。

🎭 分区表的常见误区

误区 1：分区越多越好

不对。分区数量过多（成百上千）会导致：

  • 查询计划变复杂，规划时间变长
  • autovacuum 工作负担加剧
  • pg_class 元数据膨胀

经验值：单表分区数最好控制在 100 个以内，至多不超过 1000 个。

误区 2：分区就是分布式

不对。分区表仍然在同一台机器上！
它解决的是单机大表的问题，不是水平扩展——扩展要靠 Citus / partman + FDW 或者应用层分库分表。

误区 3：随便找个列就能当分区键

不对。分区键应当满足：

  • 是查询条件的高频过滤列（否则不走裁剪）
  • 值分布相对均匀（避免某个分区过大）
  • 不会频繁 UPDATE（跨分区 UPDATE 代价高）

⚙️ 几个容易被忽视的技巧

1. 启用分区间并行与分区裁剪

2. 为每个分区建独立索引

分区表的索引本质上是每个子表各自的索引，必须保证每个子分区都建了，否则计划器会放弃走索引：

3. DETACH CONCURRENTLY 避免锁库

🚦 什么时候不要分区？

  • 表小于 100GB：收益不明显
  • 没有明确的裁剪列：反而让查询变慢
  • 高度关联的小表：JOIN 代价会放大
  • 频繁做跨分区 UPDATE：触发行迁移，代价昂贵

一句话：分区表是给”真正的大表”准备的礼物，不是万物通用的调料。

✨ 结语

分区表不是银弹，而是一套对抗时间的武器——
它承认一个事实：数据会越积越多，而我们对数据的关注却越来越集中在”新”的部分。

它用”拆”的智慧对抗”大”的原罪；
用”裁”的艺术成全”查”的优雅。

好的分区方案，让一张 100 亿行的表查得像 1000 万行一样快，删得像 DROP TABLE 一样爽。
