共享缓冲区shared_buffers的秘密世界

每一次 SELECT、每一次 UPDATE，都可能在 PostgreSQL 的内存里上演一场”缓存的戏剧”。这场戏的舞台，就是 shared_buffers——一块看似平静、实则暗流涌动的共享内存。

🎭 一次查询的内存旅程

很多人以为这条 SQL 就是”磁盘 → 返回”。实际上它要经过：

shared_buffers 位于 PostgreSQL 进程组的共享内存段中，所有 backend 进程都能读写。
它是数据库自己管理的一级缓存，下面还有操作系统的 Page Cache 作为二级缓存。

📐 shared_buffers 的内部结构

shared_buffers 被切成固定 8KB 大小的 buffer（与数据页一致）。
每个 buffer 配有一个描述符（BufferDesc）：

最关键的三个字段：

  • refcount：有多少 backend 正在使用
  • usage_count：访问热度（0~5）
  • dirty bit：是否被修改过

🧭 Buffer 如何被找到：Hash Table

shared_buffers 通过一个哈希表把 BufferTag → buf_id 映射起来：

为了减少锁竞争，这个哈希表被拆成 128 个分区，每个分区有自己的轻量级锁（LWLock）。
命中率高的系统，这一步几乎无锁。

🔄 Clock Sweep：PG 的 LRU 替代品

经典教科书上的 LRU 需要维护一个全局链表，在多核高并发环境下锁冲突严重。
PostgreSQL 用了一个更便宜的近似算法：Clock Sweep（时钟扫描）。

规则很朴素：

  1. 每次需要驱逐一个 buffer，时钟指针 hand 转一圈
  2. usage_count > 0：递减它，跳过
  3. usage_count == 0 且 refcount == 0：驱逐它

访问一次 buffer，usage_count 就 +1（最大 5）。所以热数据自然留下来，冷数据自然被挤出，无需维护复杂链表。

🧊 脏页的命运：刷还是不刷？

一个 buffer 被修改过，叫脏页（dirty page）。它不会立刻写回磁盘，因为：

WAL 已经保证了持久性，数据页落盘可以”从容不迫”。

脏页会在以下时刻被刷回：

触发者 触发条件
Checkpointer 周期性刷所有脏页（最主要的刷盘者）
Bgwriter 后台慢慢刷，减少 backend 同步等待
Backend 找不到空闲 buffer，被迫自己刷一页出来

Backend 自己刷盘是最糟糕的情况——它让一次普通查询被”勒索”去写磁盘。
调大 shared_buffers 和 bgwriter_lru_maxpages 能显著减少这种情况。

🎯 Ring Buffer：为顺序扫描设计的小屋

假设有一个顺序扫描大表的查询：

如果它把 shared_buffers 里所有热数据都挤出去，那缓存就完蛋了。
PostgreSQL 很聪明——对大规模顺序扫描，它使用一个小的环形缓冲（Ring Buffer）：

操作 Ring 大小
大表顺序扫描 256KB
COPY 16MB
CREATE INDEX 16MB

大扫描不会污染主缓存，是数据库工程师的温柔。

🧪 观察缓存命中情况

  • blks_read：从操作系统（或磁盘）读了多少块
  • blks_hit：shared_buffers 命中多少块

健康的 OLTP 系统，命中率应该 > 99%；<95% 就要考虑加内存或者重新审视查询模式。

更细的观察：pg_buffercache

能看到当前 shared_buffers 里哪些表占了多少空间——表级别的缓存画像。

🎚️ shared_buffers 应该设多大？

教科书建议

总内存的 25%

现实建议

场景 建议值
内存 ≤ 16GB 25%（4GB 左右）
内存 16~64GB 2533%（820GB）
内存 ≥ 64GB 8~16GB 为基础，再结合 huge_pages
只读分析库 可更高，接近 40%

为什么不是 80%？
因为操作系统的 Page Cache 也在缓存数据，二者太大容易互相挤兑，还会浪费内存拷贝。

最佳实践：shared_buffers 留一块”热中心”；其余交给操作系统做二级缓存。

别忘了 huge_pages

🧯 常见误区

误区 1：shared_buffers 越大越好

不对。过大的 shared_buffers 会让：

  • 清理 dirty buffer 的时间变长
  • checkpoint 抖动更严重
  • OS Page Cache 空间被挤压

误区 2：缓存命中率接近 100% 就万事大吉

不对。命中率高可能只是工作集小，并不代表没慢查询。
永远要结合 pg_stat_statements 一起看。

误区 3：修改 shared_buffers 不用重启

错。shared_buffers 是 postmaster 启动时分配的共享内存，必须重启才能生效。

🛠️ 预热缓存：pg_prewarm

重启后缓存是冷的，第一批查询会很慢。PostgreSQL 提供了 pg_prewarm 扩展：

还可以开启 pg_prewarm.autoprewarm = on，在关闭前保存 buffer 列表，启动后自动预热。

✨ 结语

shared_buffers 像一座城市的中央车站：

  • 所有数据都要经过它
  • 它的容量决定城市的”心跳速度”
  • 它的策略决定谁能留宿、谁将离开

一个 DBA 的修养，往往就体现在他如何理解这座车站的秩序。

不懂 shared_buffers 的数据库工程师，就像不懂交通的城市规划师。
