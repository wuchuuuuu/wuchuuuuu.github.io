VACUUM的前世今生：PostgreSQL最温柔的清道夫
梧杵 化神洞玄

MVCC 给了 PostgreSQL 读写不互斥的优雅，也留下了”死元组”这个后遗症。如何优雅地清理它们？答案是 VACUUM——这位温柔的清道夫，默默维持着整个数据库的秩序。

🍂 一切从一条 UPDATE 说起

在 PostgreSQL 里，这条看似简单的 SQL 其实做了三件事：

  1. 把原来那行标记为”删除”（设置 xmax）
  2. 插入一行新版本（设置 xmin）
  3. 让所有索引指向新版本（HOT update 例外）

结果是：磁盘上多出了一行，原来那行并没有真正消失。

这些”看得见但再也用不到“的元组，就是死元组（dead tuple）。

如果没有任何回收机制，数据库空间会像暴雪后的街道一样被垃圾塞满。

🧹 VACUUM：负责收拾残局的人

VACUUM 的工作，用一句话概括：

扫描表，找到死元组对应的空间，标记为可重用。

注意它做的不是：

  • ❌ 把表变小（除非加 FULL）
  • ❌ 把空间归还给操作系统
  • ❌ 阻塞读写（普通 VACUUM 不会）

它做的是：

  • ✅ 把死元组占用的槽位回收进 FSM（Free Space Map）
  • ✅ 更新 VM（Visibility Map），让 Index Only Scan 更有效
  • ✅ 推进 relfrozenxid，防止事务 ID 回卷

🧬 VACUUM 的三种形态

1. VACUUM（普通版）

最常见的，不锁表、在线运行：

只回收死元组占用的空间，不整理碎片。表的物理大小不变，只是内部出现了”空洞”。

2. VACUUM FULL（重型武器）

会重写整张表：创建一张新表，把活元组顺序写入，最后替换旧表。
效果是表变得紧凑、空间归还 OS。

代价：需要 ACCESS EXCLUSIVE LOCK，期间无法读写。

🧊 FREEZE 与事务 ID 回卷

PostgreSQL 的事务 ID 是 32 位无符号整数，最大约 42 亿。

用完怎么办？回卷（wraparound）——一旦发生，老事务创建的行会突然”从未来看见自己是未来”，导致数据损坏。

为了防止这件事，VACUUM 会把”非常老”的事务 ID 替换成一个特殊的 FrozenXid，这个过程叫 FREEZE。

触发阈值由 vacuum_freeze_min_age（默认 5000 万）和 autovacuum_freeze_max_age（默认 2 亿）控制。

🧨 常见的 VACUUM 踩坑

坑 1：长事务阻止清理

只要有一个事务号比某元组的 xmax 还小，VACUUM 就不敢清理它——这就是长事务的原罪。

排查：

一个 idle in transaction 连接，能让整个数据库的 VACUUM 集体罢工。

坑 2：复制槽持有 WAL

未消费的逻辑复制槽会持续持有 WAL 及其指向的事务，效果等同于长事务：

不用的槽及时 pg_drop_replication_slot()。

坑 3：大表 VACUUM FULL 锁死业务

VACUUM FULL 在生产线上几乎是禁术。更优雅的选择：

  • pg_repack 扩展：不阻塞业务地重建表
  • CLUSTER：需要索引，但也会锁表
  • PG 14+ 的 REINDEX ... CONCURRENTLY 用于索引膨胀

✨ 结语

VACUUM 并不是一个”可有可无的维护操作”，它是 PostgreSQL 的循环系统——
没有它，MVCC 的血液会凝固；没有它，事务 ID 会耗尽；没有它，磁盘会慢慢窒息。

它朴素得像清晨的清洁工，却承担着城市运转的底层秩序。

理解 VACUUM，不只是了解一条命令，而是读懂 PostgreSQL 的生命节律。
