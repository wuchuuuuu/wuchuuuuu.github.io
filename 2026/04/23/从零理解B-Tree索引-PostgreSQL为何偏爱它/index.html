🌳 为什么选”B”树而不是”二叉”树？

初学者常问：为什么不用平衡二叉搜索树（BST）或红黑树呢？

因为磁盘不是内存。

内存按字节寻址，磁盘按页（通常 8KB）读取。
如果用二叉树，1000 万个键需要 log₂(10⁷) ≈ 23 层——意味着 23 次磁盘 I/O。

而 B-Tree 的每个节点都是一页（PostgreSQL 是 8KB），一页能容纳数百个键。
假设一页能放 256 个键，那么 1000 万个键只需要：

$$
\log_{256}(10^7) \approx 3
$$

仅 3 层树就能索引 1000 万行数据，磁盘 I/O 少了近 10 倍。

B-Tree 的哲学：每次磁盘 I/O，尽可能多带回信息。

PostgreSQL 使用的实际上是 B+Tree 的变种，叶子节点之间通过链表连接，方便范围扫描：

关键特性：

  • Root → Internal → Leaf 三种节点类型
  • 所有真实数据（heap TID）只存在于叶子节点
  • 叶子节点之间通过 btpo_prev / btpo_next 相连，范围查询只需要顺着链表读
  • 每一页都是 8KB，按需分裂与合并

🧪 B-Tree 不擅长什么？

虽然万能，但它不是银弹：

场景 适用索引 原因
等值 / 范围查询 ✅ B-Tree 天生擅长
前缀匹配 LIKE 'ab%' ✅ B-Tree 能走范围
中间匹配 LIKE '%ab%' ❌ B-Tree 需要 pg_trgm + GIN
全文搜索 ❌ B-Tree 用 GIN + tsvector
数组包含关系 ❌ B-Tree 用 GIN
地理空间查询 ❌ B-Tree 用 GiST / SP-GiST
多维相似性搜索 ❌ B-Tree 用 GiST / pgvector(HNSW)

一句话总结：B-Tree 适合有序的数据和范围查询；其他复杂查询要找它的朋友们。

🧹 B-Tree 的阴暗面：膨胀

B-Tree 索引有一个臭名昭著的问题——膨胀（bloat）。

PostgreSQL 的 MVCC 机制决定了更新 = 插入新版本 + 旧版本待回收，索引条目也随之增加。
死元组对应的索引项被 VACUUM 清理后，空间并不会还给操作系统，而是留在索引文件里。

长此以往，一个健康的索引可能膨胀到两倍甚至更多。

排查膨胀：

治理手段：

  • REINDEX INDEX CONCURRENTLY users_pkey;（PG 12+，在线重建）
  • 设计上避免高频更新索引列
  • 监控 pg_stat_user_indexes 里的 idx_scan，删掉从不使用的索引

🛠️ 实战：如何创造一个好的索引

原则一：选择性优先

选择性 = 不同值数量 / 总行数。选择性越高，索引越有效。
gender（只有 M/F）上的索引几乎没用；email 上的索引效果极佳。

✨ 结语

B-Tree 之于数据库，就像字母表之于语言——平凡、古老，却是一切复杂的起点。

它能在 1000 万行里 3 次 I/O 精准命中；
它能让排序免费、范围无痛；
它能用最朴素的结构撑起最现代的查询。

但它也并非万能——膨胀、选择性、覆盖性，每一个都值得我们反复琢磨。

懂索引的人，看到的是数据的秩序；懂 B-Tree 的人，看到的是 I/O 的艺术。
