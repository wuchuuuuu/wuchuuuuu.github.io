1. 概览与定位

1.1 SQL Server 是什么

SQL Server 是 Microsoft 出品的关系型数据库管理系统，最早源于 1989 年与 Sybase 的合作（这就是为什么 SAP ASE 和 SQL Server 早期有大量共同代码）。从 2005 版开始，SQL Server 才完全独立于 Sybase 演进。SQL Server 2017 起支持 Linux，打破了”只在 Windows 上跑”的历史限制。

1.2 与 PostgreSQL 的核心定位差异

维度 PostgreSQL SQL Server
开源/商业 BSD 协议，完全开源 商业软件，按 core licensing
主要用户群 互联网、初创、开源生态 企业 ERP、政府、金融、传统行业
扩展能力 extension 生态极其丰富（PostGIS、TimescaleDB、Citus） 内置功能多，第三方扩展少
编程语言 PL/pgSQL、PL/Python、PL/Perl、PL/V8 T-SQL（主力）、CLR（C# 函数）
价格 免费 Enterprise 约 $14,000 / 核 / 永久
跨平台 原生支持所有 Unix/Linux/Windows 2017+ 才支持 Linux（基于 SQLPAL）

1.3 版本与 Edition

  • Express：免费，DB 大小限制 10 GB，1 核 1.4 GB 内存。适合学习。
  • Standard：核心功能，最多 24 核 / 128 GB 内存。中型应用。
  • Enterprise：全部功能，无硬件上限。Always On 自动故障转移、Columnstore、In-Memory OLTP 等高级特性必须 Enterprise。
  • Developer：功能等同 Enterprise，但仅限非生产用途，免费。学习首选。
  • Azure SQL Database：云端 PaaS 版本，按 DTU 或 vCore 计费。

💡 学习建议：直接装 Developer Edition（免费且功能完整），别用 Express，否则会缺很多关键特性比如 Columnstore。

3. 架构详解

3.1 进程模型 vs 线程模型

这是 PG 和 SQL Server 最根本的差异。

PostgreSQL — 多进程架构

Postmaster 主进程 fork 出 backend 子进程，每个连接对应一个 OS 进程。共享内存（shared memory）用于 Buffer Pool。

  • 优点：单 backend 崩溃不影响其他连接。
  • 缺点：进程切换开销大，连接数无法太高（通常 <500，需要 PgBouncer）。

SQL Server — 单进程多线程架构

整个实例就是一个 sqlservr.exe 进程。SQLOS 在用户态实现了类似 OS 的调度层，每个 CPU core 对应一个 Scheduler，管理协作式调度的 Worker。

  • 优点：连接数可达数万，线程切换开销小。
  • 缺点：单线程崩溃可能引起整个实例崩溃（实际很少发生）。

3.2 SQLOS — SQL Server 的”用户态操作系统”

SQLOS 是 SQL Server 架构中最独特的部分，PG 没有任何对应组件。它在 SQL Server 进程内重建了一套”操作系统”，向上为查询引擎提供统一的 API，向下屏蔽 Windows / Linux 的差异。

SQLOS 组件 职责 PG 对应物
Scheduler 每个 CPU core 一个，管理”可运行 Worker 队列” OS 调度（PG 不接管）
Worker 对应一个 Windows Thread 或 Linux Thread backend 进程
Memory Manager 统一管理所有内存（Buffer Pool、Plan Cache、Lock 内存等） shared_buffers + 各模块 malloc
I/O Manager 异步 IO，批量读写 8KB 数据页 OS pread/pwrite
Lock Manager 集中管理所有锁结构 分散在各 backend 的锁哈希表
Deadlock Monitor 每 5 秒扫描锁等待图，检测死锁 backend 内部检查 deadlock_timeout

5.2 聚集索引（CLUSTERED）的关键概念

这是 PG 用户最容易困惑的点：每张 SQL Server 表只能有 1 个聚集索引，且通常就是主键。聚集索引决定数据的物理排序。如果不创建聚集索引，表就是”堆表”（HEAP），性能通常更差。

📌 类比理解：

  • PG 表 = 堆表 + 索引（索引存 ctid 指向堆里的物理位置）
  • SS 表 = 聚集索引本身就是表（叶子节点是完整数据行），非聚集索引存”聚集键”指向聚集索引

聚集索引设计原则：

  • 窄：列宽要小（INT 比 NVARCHAR(100) 好），因为非聚集索引会重复存这个键
  • 唯一：避免重复键值，否则 SS 自动加 4 字节 uniquifier
  • 静态：不可变，否则修改会引发非聚集索引的级联更新
  • 递增：避免页分裂（page split），IDENTITY 是天然好选择
  • 非空：聚集键不能是 NULL

⚠️ 反模式：用 NEWID()（UUID）做聚集键。UUID 是随机分布的，会导致严重的页分裂和索引碎片。如果非要用 UUID，请用 NEWSEQUENTIALID()（顺序 UUID）。

12.1 动态管理视图（DMV）速查

DMV（Dynamic Management Views）是 SQL Server 暴露内部运行状态的标准接口，对应 PG 的 pg_stat_* 系列视图，但覆盖面更广、粒度更细。

类别 DMV 用途
会话与请求 sys.dm_exec_sessions 当前所有会话信息（≈ pg_stat_activity）
会话与请求 sys.dm_exec_requests 当前正在执行的请求
会话与请求 sys.dm_exec_connections 网络连接信息
等待事件 sys.dm_os_wait_stats 累计等待事件统计（最重要的调优入口）
等待事件 sys.dm_os_waiting_tasks 当前正在等待的任务
锁与阻塞 sys.dm_tran_locks 当前持有的所有锁
锁与阻塞 sys.dm_exec_requests 中的 blocking_session_id 阻塞链路追踪
IO sys.dm_io_virtual_file_stats 数据/日志文件 IO 统计
内存 sys.dm_os_memory_clerks 各内存模块的占用
缓存 sys.dm_exec_cached_plans 计划缓存
索引 sys.dm_db_index_usage_stats 索引使用频次（找出未使用索引）
索引 sys.dm_db_missing_index_* 缺失索引建议

12.3 常见等待事件解读

等待类型 含义 PG 类比
PAGEIOLATCH_* 等待数据页从磁盘读入内存（IO 瓶颈） IO Wait
PAGELATCH_* 等待内存页面 latch（常见于 tempdb 争用） LWLock
LCK_M_* 等待行/页/表锁 Lock
CXPACKET / CXCONSUMER 并行查询线程间同步 无对应
ASYNC_NETWORK_IO 客户端没及时收数据 ClientRead
WRITELOG 等待日志刷盘 WALWrite
RESOURCE_SEMAPHORE 等待内存授予（大查询排队） 类似 work_mem 不足

12.4 找出 TOP 慢查询（Plan Cache 视角）

💡 与 PG pg_stat_statements 对比：DMV 的 dm_exec_query_stats 只保留 Plan Cache 中的查询，重启或计划过期就会丢失统计。真正用来做长期分析，应该开 Query Store（见第 8 章）。

写在最后

从 PG 切到 SQL Server，最大的”思维切换”集中在四件事上：

  1. 聚集索引 = 表本身：表的物理结构由聚集索引决定，这跟 PG 的堆表模型完全不同。设计表的第一刻就要想清楚聚集键怎么选。
  2. tempdb 是命门：不像 PG 把临时数据散到各处，SQL Server 把版本存储、临时表、排序溢出全塞进 tempdb，这里被搞挂，整个实例都受影响。
  3. Login 与 User 分层：习惯了 PG 的 role-everywhere 之后，会在权限模型上反复踩坑。
  4. Query Store 真香：这是 SQL Server 给 DBA 的最大礼物——开启就有，且性价比极高，PG 只能羡慕。

如果你正打算做反向迁移（PG → SQL Server）或多引擎共存的工作，建议把第 4、5、7、12 章作为高频回顾区。其他章节作为查询手册即可。
